## Why this exists

Core §7 asks every site for self-service export and delete. Export shipped
with the shell pages (`/app/settings/data`, `GET /api/vault/export`).
Deletion did not: it must remove every version of every original and every
derived copy in Backblaze (Media standard rule 19), and Family History has no
B2 delete path yet. A delete button that left files behind would break the
promise, so `/app/settings/data` and `/delete-account` say deletion is by
request through the support desk for now.

## Current truth

- No account-deletion code. `convex/vaultMigration.ts` `OWNED_TABLES` lists
  every owner table (the right list to delete from).
- Media rows pin B2 originals and renditions by `versionId`
  (`media.b2Original`, `media.b2Renditions`); `lib/media/evidenceB2.ts` signs
  reads and uploads but has no delete.

## Next safe action

1. Add a version-exact B2 delete to `lib/media/evidenceB2.ts` (copy the
   pattern from Plants `lib/media/b2.ts` / `copyCleanup.ts`), unit-tested
   against a mock.
2. A `deleting` account state that gates every byte path first, then an
   internal action that deletes media versions, then rows table by table in
   batches of 200 from `OWNED_TABLES`, resumable, with a final empty check.
3. Typed confirmation on `/app/settings/data`; update `/delete-account`.
4. Prove it in Local Sandbox on synthetic records only.

## Constraints

Never run against production data in development. The first real deletion is
a person's own request.
