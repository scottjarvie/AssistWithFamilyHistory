## Why this exists

Tool names, descriptions, required permissions, aliases, and consent language
come from `lib/mcp/catalog.ts`, but the actual Zod input schemas are registered
inside `convex/httpRoutes/mcp.ts`. Response shapes, backing operations, error
codes, batch behavior, provenance, receipts, and replay rules are distributed
across handlers and tests. A catalog change can therefore look internally
consistent while changing the wire contract or recovery behavior.

## Current truth

The current release has sixteen canonical tools, twelve compatibility aliases,
and seven person-approved permissions. Batch saves retain successful rows and
return per-item failures; callers retry only failed rows with a new top-level
operation id. Create keys and command receipts prevent duplicate mutations.
Public and machine truth now fail verification when tool names or authority
tiers drift, but there is no version/fingerprint for the complete operation
contract and no generated comparison of request/response/error behavior.

There is no stable public HTTP API, SDK, or CLI. Contract parity must describe
those surfaces as absent; it must not create them merely to make a checklist
look complete.

The 2026-07-28 protocol transport itself is current: the production route uses
`@modelcontextprotocol/server` 2.0.0's `createMcpHandler` with a fresh
grant-filtered server per request. Modern calls carry their version, client
identity, and capabilities per request; they do not depend on `initialize`,
`notifications/initialized`, `Mcp-Session-Id`, or process-local session state.
The retained 2025 fallback is also stateless. The twelve old tool-name aliases
have reconnect evidence from clients that predate namespacing, but no named
client lifecycle currently proves that the broader 2025 protocol fallback is
still required.

The SDK supplies `server/discover`, validates `Mcp-Method`/`Mcp-Name` against
modern request bodies, and fills cacheable results with the conservative
`ttlMs: 0` and `cacheScope: "private"` defaults. Family History tests prove a
modern official-client connection, repeated sessionless calls, immediate grant
narrowing, and immediate revocation, but do not directly assert the discover
payload, cache fields on a granted catalog, or header-mismatch refusals. Those
are SDK-backed properties rather than product-pinned contracts today.

Every successful and refused tool call returns `structuredContent` as well as a
text block. None of the sixteen tool registrations advertises an
`outputSchema`, however, and the otherwise accurate read/write annotations omit
`openWorldHint: false` for these closed-world first-party vault operations.
Adding useful result schemas is a cross-tool wire-contract change, not a small
documentation fix.

OAuth access tokens are verified against one exact configured issuer, and
stored product grants remain bound to issuer, subject, and client id and are
re-resolved on every call. RFC 9207's authorization-response `iss` check is a
client responsibility and therefore still needs proof in a real named-client
lifecycle. Strict CIMD validation exists in source but is not on the current
request path; production Clerk advertises DCR. Under the final specification,
CIMD is the standard direction and DCR must be described only as a temporary
compatibility path, not the preferred architecture.

The audit did not justify a seventeenth product tool. Stored-grant revocation,
exact operation-id replay with different-input collision rejection, bounded
first-party media delivery, and the existing named-client acceptance boundary
remain unchanged.

## Bounded scope

- Inventory exactly the sixteen existing canonical tools and their retained
  aliases.
- For each tool, record backing Convex operation, read/write posture, required
  and conditional permission, record boundary, request schema, result shape,
  batch limits, operation-id/create-key behavior, provenance, errors and caller
  recovery, reversibility, human confirmation, and current proof.
- Give the inventory a deterministic version or fingerprint and fail checks
  when transport registration, handlers, `/ai`, `/ai.txt`, the capability
  manifest, or lifecycle harness diverge from it.
- Pin the 2026-07-28 transport behavior with Family History-owned checks for a
  useful `server/discover` response, no modern initialize/session dependency,
  required private cache hints, and `Mcp-Method`/`Mcp-Name` presence and
  mismatch rejection.
- Add truthful output schemas for every existing tool and complete annotations,
  including the closed-world hint, without changing any current result shape.
- Record whether a named real client still needs 2025 protocol fallback; retain
  it until that evidence exists, then remove it or document the compatibility
  dependency explicitly. Tool-name aliases remain a separate decision.
- Make CIMD the documented standard direction, describe provider DCR only as a
  compatibility bridge, and require the named-client lifecycle to prove RFC
  9207 issuer validation before code redemption.
- Preserve current default/person-approved/reserved authority and every privacy,
  living-person, review, rights, and owner boundary.

## Exclusions

- No new MCP tool, generic CRUD API, OpenAPI claim, SDK, CLI, permission,
  raised-authority path, admin/delete/publish/merge/share/external-provider
  operation, or alias removal.
- No Backblaze credential, provider setting, production data, or named-client
  mutation.

## Definition of done

- [ ] Every existing tool has one reviewable operation-contract entry.
- [ ] Generated or structural checks catch schema, response, error, replay,
      alias, permission, public-guide, and machine-manifest drift.
- [ ] Batch partial success and retry semantics remain explicit and tested.
- [ ] Absent API/SDK/CLI surfaces are reported as absent, not implied.
- [ ] Full verification, protected PR, exact-main CI/deploy, live machine-path
      proof, and independent audit remain separate evidence layers.

## Evidence

- 2026-09-03 source audit: catalog names/descriptions/scopes live in
  `lib/mcp/catalog.ts`; Zod inputs and registrations live in
  `convex/httpRoutes/mcp.ts`; responses/errors/replay are distributed through
  handlers and tests.
- The current branch proves name, permission, public-guide, and machine-manifest
  parity only. It deliberately does not claim complete operation-contract
  parity before the proposed Work Order is approved and executed.
- 2026-09-03 final-spec delta audit: official `@modelcontextprotocol/server`
  2.0.0 behavior covers modern stateless serving, discovery, standard-header
  validation, and conservative cache hints. Direct product assertions for
  those seams, all sixteen output schemas, closed-world annotations, a named
  client's need for legacy protocol, and client-side RFC 9207 proof remain open.
