## Current truth

### FH-R001 · Same name and birth year overwrites a different FamilySearch person

- **What happens:** importing person B (new FamilySearch id) whose given name,
  surname and birth year match person A updates A in place and replaces A's
  FamilySearch id with B's.
- **Cause:** `convex/vaultMutations.ts:346-375` falls back to name+year when the
  id lookup misses, without checking that the candidate has a different `fsId`;
  `:378` then writes `fsId: args.fsId ?? existing?.fsId` and `:393` patches.
  Called from `lib/familysearch/importer.ts:58-70`.
- **Smallest fix:** in the fallback, skip any candidate whose `fsId` is set and
  differs from `args.fsId`; never overwrite an existing `fsId`.
  - Restart: write explicit identity-match acceptance tests. Skipping on a
    different FS id alone still allows silent name merges (no FS id on either).
- **Why it matters:** silently merges two real people and loses one identity.

### FH-R002 · Importing a related person removes living-person protection

- **What happens:** a person discovered in a source's related-people list is
  saved as deceased, even if they already existed as living.
- **Cause:** `lib/familysearch/importer.ts:198-205` sends `living: false`;
  `convex/vaultMutations.ts:381` writes `living: args.living` over the existing
  value. Public story pages then show their name (`convex/vault.ts:936-944`).
- **Smallest fix:** omit `living` for related people (unknown), and in the
  upsert never turn `living: true` into `false` without a death fact.
  - Restart: `living` is required at `convex/vaultMutations.ts:321`, so this
    needs a mutation-contract change and a safe default for an unknown person.
- **Why it matters:** living-person names can reach public pages and the AI.
  Also issue #103 (closed into this item), which adds the subject's own
  direction: `inferLiving` at `lib/familysearch/importer.ts:398` (used at `:63`)
  treats a missing death date as proof of nothing. Don't infer `living` from it.

### FH-R003 · Two children from one source overwrite each other's parent link

- **What happens:** importing child A then child B from the same record (say a
  census) re-points the father→A link to father→B.
- **Cause:** relationship keys omit the primary person:
  `lib/familysearch/importer.ts:610` (`fs-rel:${sourceKey}:parent:${name}`), same
  for spouse `:599` and child `:621`; `convex/vaultMutations.ts:906-912` finds
  the row by `importKey` and `:930-931` patches `person1`/`person2`.
- **Smallest fix:** include the anchor person's FamilySearch id in the key, as
  source and citation keys already do (`importer.ts:102`, `:110`).
- **Why it matters:** silently loses a real parent–child link.

### FH-R004 · Story context for the AI is the full human reviewer bundle

- **What happens:** `family_history_get_context` with `kind: "story"` returns
  the reviewer view, including the person's notes when living, every related
  person document, and media that has not been privacy-reviewed.
- **Cause:** `convex/httpRoutes/mcp.ts:790-796` returns `vault.getStoryReview`;
  `buildStoryBundle` spreads the whole person (`convex/vault.ts:761-768`), all
  related media when not public (`:788-792`) and full `relatedPerson` docs
  (`:793-803`). Only `replacedB2Files` is stripped. The bundle caps media at
  six items, but those six can still be unreviewed or living-person media.
- **Smallest fix:** an AI projection that applies the same living-person and
  media `aiUseAllowed` gates as `convex/mcpEvidence.ts`.
- **Why it matters:** private and living-person data reaches the AI.

### FH-R008 · Documents stored under a FamilySearch id skip the living check

- **What happens:** a living person's PS/CST document filed under their
  FamilySearch id (not the Convex id) is sent to the AI.
- **Cause:** `convex/mcpEvidence.ts:235-239` resolves the person only with
  `normalizeId("persons", …)`, which returns null for an FS id, so the check is
  skipped. `convex/documents.ts:38-65` accepts either id and `:107`/`:143`
  stores it verbatim.
- **Smallest fix:** fall back to the `by_fsId` index, and refuse when no owned
  person is found.
- **Why it matters:** bypasses the rule that living people stay out of AI context.

### FH-R006 · A selected-people grant can read the whole vault through brief and search

- **What happens:** an AI approved for two people can call brief or search
  and get results about everyone.
- **Cause:** `boundaryPermits` allows any call naming no person
  (`lib/mcp/authorize.ts:340-352`, `:351`); brief and search are registered at
  `convex/httpRoutes/mcp.ts:750-762` and `getBrief`/`search` take only the
  principal (`convex/mcpFamilyHistory.ts:1216-1302`), never the boundary.
- **Fix already written:** `backup/fh89-tenant-fail-closed-20261021` (PR #89),
  commit `4839963` "Scope MCP brief and search to the grant's record boundary".
  Kept as a feature in AWF-0080.
- **Why it matters:** a narrow grant is the main privacy promise of the AI page.

### From open issues (triaged 2026-11-06 on `44041e2`)

- **#99 Hosted import says raw captures were saved without keeping them.**
  `lib/storage/fileStorage.ts:371` returns a path without writing;
  `app/api/import/route.ts:104-120` replies "Raw artifacts were saved".
  Smallest fix: store the capture durably and record its reference on the
  import run, or return an honest partial receipt.
- **#100 Editing a story keeps the old second-review approval.**
  `convex/vaultMutations.ts:1740-1748` leaves `secondReviewedAt`;
  `lib/stories/publishSafety.ts:472` accepts any timestamp. Smallest fix: clear
  `secondReviewedAt` on every content, person or evidence change (draft update,
  upsert and MCP update), or bind it to a content hash.
- **#104 Heuristic source relationships stored as accepted Biological.**
  `lib/familysearch/importer.ts:603-618` sets `childRelationType: "Biological"`
  from role text. Smallest fix: leave the type unknown and mark it proposed
  unless the capture states it. Same function as FH-R003; fix together.
