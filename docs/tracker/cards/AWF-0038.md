## Why this exists

The first remote MCP release is useful, not universal. A conforming chosen AI
still needs a safe way to identify itself and begin OAuth without Scott or an
operator manually creating a new client for every connection. That onboarding
must preserve recognizable client identity, exact redirect validation,
explicit consent, cleanup, and the person's narrow Family History grant.

## Current truth

Production exposes one stateless Streamable HTTP `/mcp` resource with a real
OAuth protected-resource challenge, sixteen canonical Family History workflow
tools, twelve compatibility aliases, and seven separately approved product
permissions.
One manually created disposable public PKCE client completed consent,
brief/search, durable research-to-story saves, correction, normal UI reflection,
and exact cleanup.

**CONFIRMED 2026-08-17: Clerk production Dynamic Client Registration is live.**
An independent read-only probe of
`https://clerk.assistwithfamilyhistory.com/.well-known/oauth-authorization-server`
returned
`"registration_endpoint": "https://clerk.assistwithfamilyhistory.com/oauth/register"`,
alongside authorization, token, revocation, introspection, JWKS, and PKCE. The
metadata still does **not** advertise `client_id_metadata_document_supported`.

This resolves the onboarding question that had been open since 2026-08-16, when
the same probe found neither. **DCR is the approved soft-launch path**: a
conforming client can now self-register and begin OAuth without anyone
hand-creating a client for it. **CIMD is deferred** — it stays the preferred
long-term client identifier, and the strict validation in
`lib/mcp/clientMetadata.ts` and `convex/mcpClientTrust.ts` stays ready for it,
but it is no longer a launch blocker and no work is queued against it.

Registration is not authority. Every request still resolves the person's own
product grant and fails closed without one.

**Correction of record, 2026-09-03:** the product does not currently receive a
trustworthy signal that an opaque `client_id` came from provider DCR, nor does
it import Clerk's registration inventory. `mcpClientRegistrations`, the
50-registration cap, and 30-day expiry belong to the strict local CIMD
validator/cache and test fixtures; no request path calls that validator today.
The transport therefore records observed clients with `manual` provenance.
Clerk's DCR endpoint is live and useful, but the earlier claim that every DCR
client is recorded untrusted in a bounded owner-visible product inventory was
not supported by the code or provider evidence.

Broad client compatibility, reconnect/refresh, mobile setup, fresh-device email,
and immediate issued-JWT revocation against the deployed site remain unproved.
AWF-0034 owns the material revocation choice.

## Requirements

- Onboard through the provider's live DCR endpoint for soft launch without
  treating its opaque client id as proof of provenance or product authority.
- Prefer a stable HTTPS Client ID Metadata Document as the client identifier
  when the provider supports it, following the current MCP authorization and
  OAuth metadata-document security requirements. Deferred, not abandoned.
- Validate exact client id, metadata JSON, redirect URIs, PKCE posture, size,
  redirects, cache behavior, and SSRF boundaries before consent.
- Keep manual pre-registration only for bounded acceptance or an exact client
  whose proven workflow requires it.
- Preserve one canonical stateless endpoint and the existing idempotency,
  bounded reads, provenance, and correction paths.
- Derive identity and vault ownership from the verified caller; accept no owner,
  user, workspace, vault, or tenant selector from a client.
- Keep anonymous requests fail-closed with the real protected-resource
  challenge and keep wrong issuer/resource/subject shapes rejected.
- Do not treat provider identity scopes as Family History authority; AWF-0040
  supplies the separately enforced product grant.
- Prove each compatibility claim with the exact client, metadata/registration
  path, protocol version, auth flow, normal UI/audit reflection, revoke/
  reconnect result, and exact synthetic cleanup.

## Next safe action

Run the exact named-client lifecycle against the canonical apex endpoint and
record what the client and provider actually expose about registration. If
owner-visible registration inventory is still needed after that proof, design a
provider-backed inventory or explicit client-attestation boundary; do not label
the existing CIMD cache as DCR inventory and do not widen product grants.

  request compatibility, sixteen namespaced workflow tools, one manually
  registered disposable PKCE client, human/machine guides, and — confirmed live
  at the provider on 2026-08-17 — a DCR registration endpoint.
- **Partial:** DCR onboarding through one exact named client, trustworthy
  registration provenance/inventory, broad clients, reconnect/refresh,
  fresh-device email, mobile setup, and the joined lifecycle.

  support. The validation code for it exists and is unused.
- **Later:** names for unproved clients, cross-family collaboration, destructive
  account/data work, publication, merges, or external provider actions; these
  are not granted by protocol compatibility.
