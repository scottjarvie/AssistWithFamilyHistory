## Why this exists

The first remote MCP release is useful, not universal. A conforming chosen AI
still needs a safe way to identify itself and begin OAuth without Scott or an
operator manually creating a new client for every connection. That onboarding
must preserve recognizable client identity, exact redirect validation,
explicit consent, cleanup, and the person's narrow Family History grant.

## Current truth

Production exposes one stateless Streamable HTTP `/mcp` resource with a real
OAuth protected-resource challenge and twelve Family History workflow tools.
One manually created disposable public PKCE client completed consent,
brief/search, durable research-to-story saves, correction, normal UI reflection,
and exact cleanup.

Read-only live probes on 2026-08-16 found that Clerk's authorization-server and
OpenID metadata advertise authorization, token, revocation, introspection,
JWKS, and PKCE, but neither `client_id_metadata_document_supported: true` nor a
`registration_endpoint`. The current path is therefore not Client ID Metadata
Document or DCR onboarding. Broad client compatibility, reconnect/refresh,
mobile setup, fresh-device email, product scopes, and immediate issued-JWT
revocation remain unproved. AWF-0034 owns the material revocation choice.

## Requirements

- Prefer a stable HTTPS Client ID Metadata Document as the client identifier,
  following the current MCP authorization and OAuth metadata-document security
  requirements.
- Validate exact client id, metadata JSON, redirect URIs, PKCE posture, size,
  redirects, cache behavior, and SSRF boundaries before consent.
- Use DCR only as a compatibility fallback, with safe default scopes,
  registration rate limits, owner/admin inventory, expiry, and cleanup.
- Keep manual pre-registration only for bounded acceptance or an exact client
  whose proven workflow requires it.
- Preserve one canonical stateless endpoint and the existing idempotency,
  bounded reads, provenance, and correction paths.
- Derive identity and vault ownership from the verified caller; accept no owner,
  user, workspace, vault, or tenant selector from a client.
- Keep anonymous requests fail-closed with the real protected-resource
  challenge and keep wrong issuer/resource/subject shapes rejected.
- Do not treat provider identity scopes as Family History authority; AWF-0040
  supplies the separately enforced product grant.
- Prove each compatibility claim with the exact client, metadata/registration
  path, protocol version, auth flow, normal UI/audit reflection, revoke/
  reconnect result, and exact synthetic cleanup.

## Next safe action

After Scott approves AWF-WO-011, run a read-only architecture and threat-model
spike comparing provider-native CIMD support, a mature reviewed authorization
adapter/gateway, and bounded DCR fallback. Do not enable DCR, change token
format, register a production client, or build a handwritten token server
during the spike.

## Definition of done

- [ ] The authorization server supports and advertises Client ID Metadata
      Documents, with DCR available only as the documented compatibility
      fallback where required.
- [ ] Client metadata fetching and registration fail safely for redirects,
      malformed JSON, redirect mismatch, SSRF, over-size, replay, and abuse.
- [ ] Modern and retained fallback HTTP requests pass without server sessions,
      stale proxy headers, or changed tool semantics.
- [ ] OAuth challenge and server-derived owner isolation still fail closed.
- [ ] One compatible client completes the bounded workflow, immediate revoke,
      reconnect, and exact cleanup.
- [ ] `/mcp`, `/ai`, `/ai.txt`, `/llms.txt`, and capability docs agree on
      Current / Partial / Later truth.
- [ ] Protected PR, CI, exact-main deployment, public boundary, authenticated
      client, normal UI, cleanup, and independent-audit layers are reported
      separately.

## Boundaries

- No real family records, Scott account, unapproved provider/default/token
  change, broad scope, security weakening, secret handling, billing, DNS, or
  external publishing.
- Do not claim all clients, mobile, reconnect, revocation, or future protocol
  behavior from one client or source-level test.
