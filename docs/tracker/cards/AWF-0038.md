## Why this exists

The first remote MCP release is useful, not universal. Family History should
adopt new MCP-standard behavior when it improves real client setup or durable
research work, while keeping owner identity server-derived and refusing raw
database CRUD, broad scopes, or capability claims based only on protocol source.

## Current truth

Production exposes one stateless Streamable HTTP `/mcp` resource with a real
OAuth challenge and twelve Family History workflow tools. Modern 2026-07-28
requests and a stateless 2025-era fallback share one tool factory. One
disposable named PKCE client completed consent, brief/search, durable
research-to-story saves, correction, normal UI reflection, and exact cleanup.
`GET /mcp` currently returns a small plain-text pointer to `/ai`; `/ai` and
`/ai.txt` state the client and revocation limits honestly.

Broad client compatibility, dynamic registration, reconnect/refresh, mobile
setup, fresh-device email, newer discovery/catalog conventions, and immediate
issued-JWT revocation are not proven. AWF-0034 owns the material revocation
choice. AWF-0037 owns the browser-host-blocked joined Queue acceptance.

## Requirements

- Start from a concrete MCP-standard or client workflow improvement, not a
  speculative protocol checklist.
- Preserve one canonical stateless endpoint and the existing product-native
  tool vocabulary, idempotency, bounded reads, provenance, and correction paths.
- Derive identity and vault ownership from the verified caller; accept no owner,
  user, workspace, vault, or tenant selector from a client.
- Keep anonymous requests fail-closed with the real protected-resource
  challenge and keep wrong issuer/resource/subject shapes rejected.
- Make the non-POST `/mcp` response helpful only after the server behavior is
  implemented; setup detail remains at `/ai` and machine guidance at `/ai.txt`.
- Prove each compatibility claim with the exact client, protocol version,
  auth flow, normal UI/audit reflection, and exact synthetic cleanup.

## Next safe action

After AWF-0037's joined acceptance can run, compare the currently deployed
transport against the next concrete MCP-standard/client requirement. Select
one bounded improvement, add raw HTTP and official-client regression coverage,
then update `/ai`, `/ai.txt`, and the helpful `/mcp` response only to the level
actually proven.

## Current / Partial / Later

- **Current:** stateless OAuth MCP, dual-era request compatibility, twelve
  workflow-native tools, one production PKCE client, and human/machine guides.
- **Partial:** broad clients, dynamic registration, reconnect/refresh,
  fresh-device email, mobile setup, and immediate issued-token revocation.
- **Later:** private media delivery, cross-family collaboration, destructive
  account/data work, publication, merges, or external provider actions; these
  are not granted by protocol compatibility.

## Definition of done

- [ ] One concrete new standard/client behavior is selected from primary MCP or
      client documentation and mapped to a real Family History user need.
- [ ] Modern and retained fallback HTTP requests pass without server sessions,
      stale proxy headers, or changed tool semantics.
- [ ] OAuth challenge and server-derived owner isolation still fail closed.
- [ ] One compatible client completes the bounded workflow and exact cleanup.
- [ ] `/mcp`, `/ai`, `/ai.txt`, `/llms.txt`, and capability docs agree on
      Current / Partial / Later truth.
- [ ] Protected PR, CI, exact-main deployment, public boundary, authenticated
      client, normal UI, cleanup, and independent-audit layers are reported
      separately.

## Boundaries

- No real family records, Scott account, provider-default change, broad scope,
  security weakening, secret handling, billing, DNS, or external publishing.
- Do not claim all clients, mobile, reconnect, revocation, or future protocol
  behavior from one client or source-level test.
