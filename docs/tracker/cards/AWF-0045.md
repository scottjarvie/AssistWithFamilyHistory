## Why this exists

Family history research runs on scanned records and photographs. A census page,
a parish register, a headstone photograph, a recorded interview — these are the
evidence. An AI that can read a person's notes but cannot see the census image
cannot do this product's core work; it can cite a title and nothing more.

`family_history_get_evidence` shipped with exactly that hole. It delivered real
text for person documents, which genuinely live in Convex, and returned
`BYTES_NOT_AVAILABLE` for everything else. That was honest, and it was also the
whole product promise going unmet.

The cause was not a missing feature in the connection. It was that **the vault
had nowhere to put a file.** A `media` row could hold a `filePath` hint or a
`url` — almost always a FamilySearch memory URL, which answers the person's own
signed-in browser and no server anywhere. So the transport's one remote fetch
was always going to fail, and there was no upload path to produce a row that
could succeed. `lib/storage/objectStore.ts` (Backblaze B2) existed with no
caller and would not have closed this either: it needs six deploy-time secrets
and a public bucket, and a publicly readable URL for a private family
photograph is the opposite of what protected delivery is for.

## Current truth

**Current in source and tests.** A person can upload a scan, photograph, record
PDF, transcript, or recording into the vault from a person's Memories tab. Bytes
land in private Convex file storage, which only owner-checked server code can
read — there is no URL to leak, guess, or hand to a model. When that item is
reviewed, its rights are usable, and AI use is allowed, the connection reads the
object directly and delivers it as an image or resource block. A 1900 census
scan now reaches a model as the actual page.

Rung 6 of the acceptance ladder — real evidence bytes — is proved locally for
the first time, end to end through the official MCP client, in
`convex/mcpLifecycleLadder.test.ts`.

**Nothing widened.** The same five gates decide a stored file that decided a
remote one: owner, grant boundary, `reviewStatus === "reviewed"`,
`aiUseAllowed === true`, and rights not restricted, plus the 2 MiB per-item and
6 MiB per-call budgets. Uploading is deliberately not the same act as allowing
AI use: every upload arrives `private`, `unreviewed`, `aiUseAllowed: false`, and
replacing an item's bytes resets its review, because the bytes under a review
are not the bytes the person reviewed.

**Still honest about what it cannot do.** An imported row that holds only a
reference still returns `BYTES_NOT_AVAILABLE` — now with a recovery that names
the real fix, which is for the person to upload the file to that item.

**Not claimed.** Nothing here has run against the deployed site. No person has
uploaded a file through a real browser, and no real family record was touched.
The upload's browser half of rung 6 remains for the live run.

## Requirements

- Bytes live in the vault, privately, with no publicly reachable URL.
- Delivery reuses the existing permission gates rather than adding a path
  around them.
- A raw storage link stays on the never-exposed list, for the model and for the
  person's own browser alike — the owner file route streams bytes and never
  returns the signed URL it used.
- A missing item and another owner's item answer identically, so no media
  surface becomes an existence oracle.
- Putting a file in the vault never widens what any connection may read.
- No new deploy-time secret or environment variable is required.

## Current / Partial / Later

- **Current in production:** private byte storage, owner-authenticated upload
  and serving, gated protected delivery, ladder rung 6. This is deployed — live
  `/updates` carries the `media-evidence-bytes` item.
- **Partial:** a person's own upload travelling through a real browser, and a
  real AI client receiving those bytes. Deployed is not the same as proved by a
  client.
- **Later:** mirroring imported FamilySearch memories into the vault (needs the
  person's session and belongs with the capture extension), thumbnails and
  derived variants, OCR or transcript extraction, and public story imagery
  served over a CDN — the job `lib/storage/objectStore.ts` was actually written
  for, and still uncalled for that reason.

## Boundaries

- No provider change, secret, environment variable, deployment, or real family
  record.
- No automatic AI permission from an upload, and no weakening of review,
  rights, living-person, or boundary gates.
- No named-client compatibility claim.
