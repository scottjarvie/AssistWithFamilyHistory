## Why this exists

Family-history research needs dense comparison, but large vaults must stay
fast, sortable, filterable, and understandable without loading everything or
discarding the user's working view.

## Current truth

People are capped in 50-row increments and operations has search, filters,
sorting, and bounded rendering. Places has search but no visible pagination.
People render cards rather than a sortable comparison table. Cursor pagination,
click-to-sort columns, remembered browser preferences, explicit saved views,
and phone drill-down are not proven.

## Scope

- Use bounded indexed queries and cursor/page contracts on all growing lists.
- Provide table-first comparison where decisions benefit, meaningful clickable
  sorting, organized filters, and stable URL/query state.
- Remember local preferences and keep account-saved views as explicit records.
- Provide phone-specific decision summaries and drill-down without horizontal
  page overflow.

## Next safe action

Measure query cardinality and index use with synthetic small/large vaults, then
choose one representative people/operations slice for the reusable contract.

## Unknowns and access limits

Production vault sizes, query costs, user preference behavior, and large-data
latency are unavailable. Do not inspect real owner data for scale testing.

## Evidence

Acceptance evidence includes synthetic 0/50/500/5000-record fixtures, query and
index bounds, deterministic pagination/sort/filter tests, saved-view ownership,
phone drill-down, and performance regression budgets.

## Definition of done

- [ ] Growing lists use bounded indexed access with deterministic continuation.
- [ ] Decision columns sort and filters remain organized and shareable.
- [ ] Browser preferences and account-saved views are distinct and tested.
- [ ] Phone views prioritize decisions without page-level horizontal scrolling.
- [ ] Empty/error/stale-query states preserve user context.
- [ ] Performance, schema, PR/CI/deployment, and independent audit proof exist.
