## Why this exists

A person must be able to disconnect a chosen AI without waiting for an already
issued bearer token to expire. Production acceptance proved client deletion and
session cleanup, but Clerk's revocation endpoint explicitly rejects JWT access
tokens. The tested token remained valid for about twenty-four hours.

## Current truth

**The product half is solved and deployed. Token lifetime no longer governs
access.** AWF-0040 made the durable product grant the authorization, and
`/mcp` re-resolves it on **every** request because the transport is stateless
(`convex/httpRoutes/mcp.ts` → `convex/mcpGrants.ts:resolveForRequest`). The
moment a person turns a connection off, the very next call from that connection
is refused with `GRANT_REVOKED` — no token has to expire first. Grant expiry is
likewise filtered at read time and never inferred from the token
(`lib/mcp/authorize.ts`). Proved by `convex/mcpGrantEnforcement.test.ts` and
`convex/mcpLifecycleLadder.test.ts`.

So the sentence this card was opened on — "an already issued access JWT keeps
working for about twenty-four hours" — is no longer true of *access to family
records*. It remains true of the **token object itself**: Clerk's revocation
endpoint still rejects JWT access tokens, so a leaked bearer cannot be killed at
the provider. What that bearer can now *do* is nothing, once the grant is gone.

**Historical acceptance receipt, unchanged:** the disposable PKCE client, refresh
path, product session, local token copy, and all synthetic Family History records
were removed. No other person or family was involved, and the only retained
identity has an empty private vault. This was a capability gap discovered through
safe live acceptance, not evidence of unauthorized access.

## Next safe action

Nothing in the repository is blocking. What remains is the **provider-side** token
posture: decide whether Clerk should mint opaque access tokens (revocable at the
provider) instead of signed JWTs. That is now defence in depth rather than the
mechanism that protects records, which lowers its urgency but not its value — a
leaked JWT should be killable, not merely useless.

Keep the existing issuer and tenant checks unchanged until that decision is made.

## Why Scott is needed

The smallest provider option changes the production Clerk OAuth token posture
from signed JWT access tokens to opaque tokens. That is a material security and
compatibility decision across every future OAuth client, not a routine local
implementation detail.

## Smallest decision or action

Approve a focused design spike comparing Clerk opaque tokens with an
application-owned active-client/revocation check, then implement only the
recommended path through a protected Work Order.

## Recommendation

Prefer Clerk's standard opaque access-token mode if it preserves stateless MCP
client compatibility and gives the resource server an authoritative active
token check. It matches the product promise most directly. If provider limits
or request latency make that infeasible, add a narrow server-side revocation
registry keyed by token/client identifiers with bounded caching.

## Alternatives and trade-offs

- **Opaque provider tokens:** strongest standard revocation semantics and least
  custom security code, but changes token validation and may add provider calls.
- **Application revocation registry:** retains local JWT verification and can
  revoke exact clients/tokens, but creates security-critical lifecycle state and
  cache-consistency work.
- **Accept expiry-only cleanup:** no implementation cost, but contradicts the
  durable chosen-AI revocation promise for up to the configured token lifetime.

## What each choice changes

- Opaque tokens change the production provider and resource-server validation
  path for OAuth clients.
- A registry adds product-owned revocation state, checks, retention, and tests.
- Expiry-only leaves deletion of a client or connection non-immediate.

## Safe default

Do not enable broad OAuth client availability. Continue isolated acceptance
only with labeled identities, disposable clients, empty workspaces, and secure
destruction of every token copy.

## Consequence of waiting

Product-side revocation may now be stated as Current: it is implemented,
deployed, and covered by tests. What must keep being stated honestly is the
narrower residue — a leaked JWT cannot be killed at the provider, and no real
client has yet proved a whole lifecycle — so this remains a soft-launch surface
for trusted testers rather than an invitation to arbitrary clients.

## Constraints

- Do not weaken exact issuer, access-token type, expiry, subject, client-ID, or
  server-derived owner checks.
- Do not broaden scopes, expose secrets, inspect real family data, or use Scott's
  account for testing.
- Treat token-format/provider changes as normal protected software plus an
  explicit production security decision.
