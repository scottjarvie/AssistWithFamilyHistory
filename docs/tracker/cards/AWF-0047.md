## Why this exists

Found while writing the context-pack conflict test for AWF-0046, on the
repository's own `tests/fixtures/capture/valid-source-v2.json`.

`classifyFactField` (`lib/familysearch/sourceFacts.ts`) types **any** birth-ish
indexed field as `factType: "birth"` — including a birth *place*:

```ts
if (/birth/i.test(combined) && /date|place|birth/i.test(label)) return "birth";
```

`findSourceFactConflicts` (`:80-124`) then compares every `birth` fact's value
against `capture.person.birthDate`, a date. So a source's "Event Place" of
`Salt Lake City, Utah, United States` is compared to `1888`, does not match, and
is reported to the person as a birth conflict.

Reproduced exactly, using only repository code and the repository's own fixture:

```
FACTS
  name  | Name        | John Jarvie
  birth | Event Place | Salt Lake City, Utah, United States
  birth | Birth Date  | 3 February 1890
CONFLICTS
  birth | Salt Lake City, Utah, United States | 1888 | Indexed source birth value differs...
  birth | 3 February 1890                     | 1888 | Indexed source birth value differs...
```

One of those two is a real disagreement. The other is a place being told it is
not a date.

## Why it matters more than it looks

This lands on the exact surface AWF-0046 just built. A person is now asked to
read two readings side by side and decide which record to believe, writing down
why. Handing them a comparison that is not a comparison wastes the most
attention-expensive moment in the product, and teaches them to click through
conflict badges without reading — which is the one habit this feature exists to
prevent.

It also reaches the AI. Every false conflict now travels in
`structured.unresolvedConflicts` in the context pack, so a connected AI will
spend real research effort reconciling a city with a year.

## Current truth

- Affects `birth` and `death` (`death|burial` fields match date-or-place the same
  way). `name` is compared name-to-name and is fine.
- The `sourceFacts` row itself is correct — it keeps the place value and its own
  label. Only the conflict verdict is wrong.
- Nothing downstream is corrupted: a false conflict can be settled like any
  other, and settling it leaves the record intact. The cost is entirely the
  person's attention and the AI's effort.

## Smallest useful next step

Compare like with like. The fact already carries `date` and `place` separately
(`pickFieldDate` / `pickFieldPlace`), so the detector has what it needs:

1. Distinguish the *field kind* when classifying — a date-bearing birth field
   versus a place-bearing one — either by splitting the fact type or by carrying
   a `fieldKind` alongside it.
2. Compare a birth-date reading to `person.birthDate` and a birth-place reading
   to the person's birth place. If the person has no recorded birth place, there
   is nothing to disagree with and no conflict should be raised.
3. Extend `scripts/check-source-facts.ts`, which already builds a conflicting
   capture, to assert that the place fact is *not* reported as a conflict.

Worth considering in the same pass: the two existing conflict reasons are
identical strings, so a person reading two badges cannot tell what differs. A
reason naming the two values would carry its own explanation.

## Definition of done

- A birth or death **place** value is never reported as conflicting with a birth
  or death **date**.
- The repository's own `valid-source-v2.json` fixture, mutated to disagree on the
  birth date, produces exactly one conflict.
- `scripts/check-source-facts.ts` asserts the absence, not only the presence.
- The comment in `scripts/test-context-pack-conflicts.ts` that currently works
  around this by selecting the date conflict explicitly is removed.
- `pnpm verify` passes.
