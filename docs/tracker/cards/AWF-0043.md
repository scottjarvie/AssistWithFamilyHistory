## Why this exists

Source compatibility and a successful tool list are not the product promise. A
person needs proof that one real compatible AI can accept narrow authority, do
source-aware work, return a reviewable result, lose access when disconnected,
recover after reconnect, and leave no synthetic residue.

## Current truth

One disposable public PKCE client previously proved explicit provider consent,
official-client tool discovery, complete saves, correction, UI reflection, and
exact cleanup in an empty test vault. AWF-WO-009 later delivered the joined
Queue/result-link source and production release, but its final authenticated
Queue round trip was blocked by the available browser hosts.

No run has proved CIMD-first onboarding, product scopes, active grant creation,
protected evidence retrieval, review-first save, immediate revoke denial,
reconnect/stale-tool recovery, or a named production client. The intended
clients—Claude, ChatGPT, Codex, Grok, Hermes, and other conforming clients—remain
capability targets only.

## Requirements

- Use a marked isolated identity/workspace and build exact cleanup before the
  first live mutation.
- Prove discovery/registration, PKCE sign-in, exact consent, active grant, tool
  scope behavior, Queue assignment, brief, evidence, result save, correction,
  normal UI visibility, and activity.

- Record exact client name/version and lifecycle evidence before adding that
  name to `/ai` or release notes.

## Current truth — 2026-08-16 (Claude, execution)

The ladder is now a runnable harness rather than a written procedure.
`pnpm mcp:lifecycle` (`scripts/mcp-lifecycle.ts`) walks all eleven points
against a configurable endpoint as a real MCP client, printing a pass/fail line
per step and a machine-readable JSON summary. It refuses to start unless the run
key matches the acceptance prefix, reads its token from the environment only,
never prints it, and pauses for the person at the two points that are genuinely
human acts — approving and revoking a connection.

Eight of the eleven rungs are additionally proved locally, with the same official
client and the same protocol pin, in `convex/mcpLifecycleLadder.test.ts`:
anonymous challenge, branded metadata, grant-filtered and empty discovery,
out-of-scope refusal without leakage, batch save with correction and stale-write
refusal, indistinguishable unknown/ungranted/invented/cross-owner refusals,
`operationId` replay, and revocation denying the very next call on a still-valid
token.

Writing the harness found two real interoperability defects that source review
had not: the empty tool catalog and the preflight refusal were both written
straight onto the wire without protocol revision 2026-07-28's required
`resultType`, so a conforming client rejected them as malformed — meaning the
carefully written "ask the person to approve this" message never reached a real
AI. `observedClientName` was also reading the `Mcp-Name` header, which carries
the tool being called, so a person's connection would have been labelled
something like `save_person`. Both are fixed and both are now guarded by
`scripts/check-mcp-contract.ts`.

`convex/mcpAcceptanceFixture.ts` now covers `mcpGrants`,
`mcpClientRegistrations`, and grant-linked `agentActivity` rows, keeping its
exact safety posture: bounded scans, visible synthetic markers, and a refusal
when anything unmarked references the marked graph.

## Recommendation

Deploy, then run the four post-deploy checks, then run the lifecycle harness —
in that order, and before touching anything in Clerk. The two Clerk items (CIMD
or DCR, and the resource-specific audience) are genuinely optional today: the
tolerant audience branch and the manual-registration path both work as shipped,
and holding them back keeps the deploy a single-variable change. If the
lifecycle run then fails, its cause is this release rather than a provider
setting changed in the same hour.

## Alternatives and trade-offs

- **Deploy and change Clerk in the same pass.** Fewer sittings, but two moving
  parts. A failure becomes ambiguous.
- **Change Clerk first, deploy later.** Enabling DCR opens a public
  client-creation surface with no product change behind it yet — the least
  attractive ordering.
- **Hold the deploy until a client is named.** Cannot work: no client can pass
  the ladder until `/app/settings/ai` exists in production, and today it 404s.

## What each choice changes

Deploying alone adds the connection centre, the fourteen `family_history_*`
tools, the twelve legacy aliases, and two unread tables — and changes nothing a
person already relies on. Enabling DCR additionally lets any client
self-register, bounded to 50 registrations and a 30-day expiry. Emitting the
resource audience additionally stops cross-resource token replay and lets a
later one-line change make the check mandatory.

## Safe default

Deploy the pinned SHA; leave both Clerk settings exactly as they are.

## Consequence of waiting

The product promise stays unprovable. No client can be honestly named on `/ai`
until one passes the full ladder, and the ladder cannot start while
`/app/settings/ai` is a 404 in production. Waiting costs nothing else — the
release is additive and reversible by redeploying the previous Vercel build.
