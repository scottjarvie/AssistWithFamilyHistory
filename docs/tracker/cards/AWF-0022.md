## Why this exists

Builders and future chosen-AI clients need one accurate account of what is
implemented, internal-only, planned, and safe to call.

## Current truth

`docs/api/route-inventory.md` lists working API-key mint/list/suspend/revoke
routes and current `apiKeys` schema, then its gap section says no API key model,
scopes, or tiers exist. The capability manifest describes keys and scope
presets as internal planning. Incoming key authentication remains unfinished.
`/llms.txt` says full OpenAPI and MCP are in development. These distinctions
are individually supportable but contradictory when read together.

## Scope

- Reconcile route inventory, capability manifest, OpenAPI skeleton, `/llms.txt`,
  Project Philosophy ledger, API Center copy, and tests to one status model.
- Distinguish key lifecycle UI from accepted incoming credentials, planning
  scopes from enforced scopes, internal APIs from public contracts, and MCP
  from ordinary HTTP routes.
- Add generation/parity checks where one canonical machine source is possible.

## Next safe action

Build a route-by-route fact table from code and tests before rewriting any
claim; coordinate with AWF-0009 rather than promising its future connection.

## Unknowns and access limits

Production key usage, external client compatibility, quotas, and incoming
authentication are unverified. Do not mint a real key for documentation proof.

## Evidence

Acceptance evidence includes code-linked route classification, generated-file
parity, contradiction search, local contracts, and public endpoint text checks.
