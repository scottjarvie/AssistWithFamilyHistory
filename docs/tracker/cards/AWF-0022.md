## Why this exists

Builders and future chosen-AI clients need one accurate account of what is
implemented, internal-only, planned, and safe to call.

## Current truth

The API-key lifecycle exists, but incoming API-key authentication and a stable
public HTTP API do not. MCP is further along: sixteen canonical tools, twelve
compatibility aliases, seven person-approved permissions, durable grants,
receipts, replay rules, and revocation are current. Before this audit, the
machine capability manifest still listed only the twelve legacy aliases and the
public `/ai` grouping omitted the evidence-write tools even though the live
catalog contained them.

This branch makes the manifest, `/ai`, `/ai.txt`, and enforced catalog agree on
tool names and authority tiers, including empty OAuth defaults, seven
person-selected permissions, no current raised tier, and the never-issuable
actions. The remaining structural gap is deeper: tool input schemas live in the
transport while descriptions/scopes live in the catalog, and there is no one
versioned inventory for request, response, errors, backing operation, batch,
provenance, receipt, or replay behavior. There is also no public SDK or CLI to
claim parity with; this Card must not create a generic API just to fill a matrix.

## Scope

- Reconcile route inventory, capability manifest, OpenAPI skeleton, `/llms.txt`,
  Project Philosophy ledger, API Center copy, and tests to one status model.
- Distinguish key lifecycle UI from accepted incoming credentials, planning
  scopes from enforced scopes, internal APIs from public contracts, and MCP
  from ordinary HTTP routes.
- Add generation/parity checks where one canonical machine source is possible.

## Next safe action

Execute the proposed bounded contract-inventory Work Order only after approval:
freeze the sixteen existing MCP operations without adding tools or widening
permissions, generate human/machine truth from it where practical, and make
schema/response/error/replay drift fail verification.

## Unknowns and access limits

Production key usage, external client compatibility, quotas, and incoming
authentication are unverified. Do not mint a real key for documentation proof.

## Evidence

Acceptance evidence includes code-linked route classification, generated-file
parity, contradiction search, local contracts, and public endpoint text checks.
