## Why this exists

Family-history research is trustworthy only when the result stays connected to
the exact source, uncertainty, and person review that support it. An AI needs a
protected way to inspect allowed files and preserve one coherent result without
silently turning a suggestion into an accepted family conclusion.

## Current truth

The twelve-tool foundation already supplies bounded brief/search/context,
replay-safe writes, stable record keys, optimistic corrections, source/citation
links, candidate/conflict fact states, private story drafts, a complete-result
transaction, and Queue continuation. Context can include metadata for reviewed
AI-allowed context and media.

There is no batch MCP evidence delivery for protected images, PDFs, audio, raw
capture artifacts, or source files. `save_complete_result` writes canonical
domain rows and permits AI-supplied evidence status, but the connection does not
yet have a single visible review bundle separating proposed interpretation from
person-accepted conclusion. Several save tools also lack a clear Family History
namespace when an assistant connects to multiple Assist products.

## Requirements

- Return one Queue/research brief with scope, relevant people/relationships,
  open questions, evidence inventory, uncertainty, review rules, grant boundary,
  and next action.
- Retrieve allowed evidence in bounded batches through MCP content/resources,
  with stable ids, privacy/rights labels, size caps, and blocked-source recovery.
- Keep user-mediated FamilySearch capture and raw-artifact privacy intact; do
  not introduce unattended provider access or private-page scraping.
- Save one idempotent proposed/reviewed result containing sources, candidate
  claims, conflicts, uncertainty, narrative sections, model/client provenance,
  review state, and Queue result links.
- Preserve granular optimistic corrections and honest blocked/failed research.
- Namespace canonical tools for Family History and provide only the shortest
  proven transition needed for existing clients to refresh safely.
- Keep publish, delete, identity merge, sharing, export, and external provider
  actions outside this tool surface.

## Next safe action

After the scope/grant matrix is approved, map the existing twelve tools and
canonical tables to the five workflow jobs in the alignment plan. Identify the
smallest additive review-result model and protected evidence adapter that avoid
duplicating the vault.

## Definition of done

- [x] One bounded call gives the AI a provenance-aware research brief.
- [x] One batch call returns protected allowed evidence or a precise recovery
      path without ordinary private-page scraping. Media the vault holds is
      delivered as real bytes (AWF-0045); media stored only as a reference
      returns `BYTES_NOT_AVAILABLE` rather than a pretend delivery.
- [x] The normal save path is idempotent, source-aware, and review-first, in
      two shapes: a batch with per-item results and the atomic all-or-nothing
      alternative.
- [x] The person can inspect and correct the result before accepted conclusions
      or publication change.
- [x] Stale correction, duplicate retry, blocked evidence, living/private data,
      and over-size cases fail safely.
- [ ] Queue completion links to the same result the normal signed-in UI shows.
      The source path exists; seeing it happen is AWF-0043's live run.

## Current truth — 2026-08-16 (Claude, execution)

`family_history_get_evidence` delivers reviewed, AI-allowed items as content
blocks inside the grant boundary, in batches, with per-item size caps and honest
skip reasons. A raw storage URL never reaches a model; resource blocks use an
opaque `familyhistory://media/<id>` URI.

`family_history_save_records` is the batch the domain actually needs: one call,
one approval, one transaction, per-item results, in-batch `createKey` cross
references, and failures caught inside the mutation so one bad row does not
discard the pass. `family_history_save_complete_result` stays as the atomic
alternative and both tool descriptions say which to reach for.

An honest limit, surfaced rather than hidden: person documents hold real text and
are delivered as text; `media` rows mostly hold a file reference, and those come
back skipped with `BYTES_NOT_AVAILABLE` and a useful recovery note. `/ai.txt` and
`/ai` both say so.

**Superseded in part — 2026-08-17.** That limit was the product's core work
going undone, so AWF-0045 closed it: the vault can now hold media bytes
privately, a person can upload a scan, and `family_history_get_evidence`
delivers it as real bytes through these same gates. A row that still holds only
a reference remains honestly `BYTES_NOT_AVAILABLE`, now with a recovery that
names the real fix.
