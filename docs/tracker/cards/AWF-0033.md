## Why this exists

A person can ask a chosen AI to research, compare evidence, or draft a story,
but the useful result currently ends at the chat boundary. Family History needs
a private, durable connection where that AI can orient to the right vault,
preserve evidence and uncertainty, save complete research results, make careful
corrections, and continue Queue work without gaining publication, deletion, or
cross-family authority.

## Current truth

The repository already has the canonical people, relationship, event, source,
citation, research, story, activity, and Queue records needed for a useful
first loop. It also has Clerk-backed owner isolation and human-managed API-key
primitives, but no stateless remote MCP route, OAuth resource challenge,
chosen-AI setup page, or domain workflow tool catalog. Internal Queue tools are
not an external connection.

Scott's 2026-08-12 coordinator delegation approves a complete first stateless
remote MCP foundation through a normal protected release, including isolated
synthetic authenticated proof. It does not authorize production family data,
secrets, billing, DNS, provider-policy changes, or another family's account.

Scott then approved the recommended production-only promotion and a retained,
clearly labeled production test identity for later authenticated MCP acceptance.
That identity may retain no family records or elevated role, and every marked
fixture, client, session, and connection must be removed after each run. The
authorization does not include named-client registration, provider-policy
changes, Scott's account, or real family data.

## Scope

- Add one stateless remote MCP endpoint with a standards-shaped OAuth resource
  challenge and server-derived owner identity.
- Give a chosen AI bounded orientation/search/context, replay-safe core domain
  saves, one-call complete-result preservation, granular corrections, and
  Queue continuation using Family History's own vocabulary.
- Save into canonical records the web UI already reads; preserve sources,
  citations, evidence status, uncertainty, activity, and human story gates.
- Add truthful human setup and agent-facing documentation with Current /
  Partial / Later boundaries.
- Prove tenant isolation, idempotency, optimistic correction conflicts,
  canonical UI visibility, and a real signed client request with synthetic data.

## Next safe action

Verify or correct the production Convex deployment path that the branded
`/mcp` proxy targets. This requires provider-level deployment configuration or
access and must not be inferred from the successful Vercel frontend deployment.
Do not create the retained test identity, register a client, or change provider
policy until the live OAuth-protected MCP edge exists and a sanctioned named
client can use it.

## Why Scott is needed

Scott or an authorized provider administrator is needed because the normal
production promotion published the exact reviewed frontend but did not publish
the corresponding Convex HTTP routes. The repository's deployment wrapper can
only deploy Convex when a correctly scoped production deploy key and target are
available. Inspecting or correcting that provider configuration would use
provider access and secrets beyond this Work Order's authorization.

## Smallest decision or action

Either have an authorized administrator verify and correct the production
Convex deploy key/target, or explicitly authorize a worker with disposable,
appropriately scoped provider access to do that verification and correction.

## Recommendation

Verify and correct only the production Convex deployment linkage first. Keep
Clerk client policy and the retained test identity separate. Once anonymous
`POST /mcp` returns the OAuth resource challenge and protected-resource
metadata resolves, a sanctioned named-client path can justify creating the
already-authorized identity.

## Alternatives and trade-offs

- **Provider administrator acts:** inspect the production build plan and make
  the existing production Convex target match the reviewed frontend. This is
  the smallest path, but it requires provider access and secret handling.
- **Explicitly authorize a scoped worker:** allow disposable provider access to
  perform the same narrow verification/correction and report exact receipts.
- **Wait:** keep the frontend documentation live and the release `In review`;
  no account, provider, or family-data state changes.

## What each choice changes

- **Provider administrator acts:** changes only production deployment linkage;
  it does not authorize OAuth client policy or any family-data access.
- **Scoped worker authorization:** expands who may use provider configuration
  and secrets, so it needs an explicit access boundary before work begins.
- **Wait:** leaves `/ai` and `/ai.txt` live while `/mcp` and discovery remain
  unavailable; the test identity is not created because it would prove nothing.

## Safe default

Wait. Keep provider policy, accounts, secrets, and family data unchanged.

## Consequence of waiting

The human and agent setup docs remain public, but chosen AIs cannot discover or
connect to the production MCP server. No user, data, or provider risk is added;
release status remains In review.

## Constraints

- The AI never supplies an owner, user, workspace, or vault identifier.
- Broad reads stay bounded and withhold living-person notes; loose context and
  media remain review-and-AI-use gated.
- No delete, identity merge, public publish, collaboration grant, or external
  FamilySearch action belongs in this first tool surface.
- Queue assignment grants Queue operations only; domain writes remain the
  separately described MCP capabilities.
- No real production data, another family's data, secret handling, billing,
  DNS, auth/provider policy mutation, or irreversible migration.
