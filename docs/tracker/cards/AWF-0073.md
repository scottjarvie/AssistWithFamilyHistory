## Why this exists

Core §4 and §17.2 step 4 require three lifecycle states (Waiting on AI, AI working, Answered)
and a separate Needs-your-input flag. Family History stores "needs you" as a fourth state, so
it cannot say "answered, and there is still a choice for you", which Core calls the common
case at the end of research. This card is the data and contract half of AWF-0060 (its Next
safe action, "map current states to the family model and write the data migration"). AWF-0060
keeps the item page, archive UI, AI-added items and AI Suggestions.

**Why backlog, not needs-you.** The labels and tab order a person will see are already decided:
the canonical Site Guide (Scott, 6 October 2026) gives the Queue as "Waiting on AI · AI working ·
Needs your input · Answered · Everything, with Needs your input as a flag." No new product
decision is needed. Recommended default: use exactly those labels.

## Migration plan

1. **Target shape.** `state: waiting_on_ai | ai_working | answered`; `needsInput: boolean`;
   `needsInputReason?: question | failed | expired | disconnected`; `requiredAction` keeps the
   exact question; `archivedAt?: number`. `condition` stays as the internal detail, with
   `awaiting_user` retired after the backfill. New index `by_owner_needs_input_updated`
   (`vaultOwnerId`, `needsInput`, `updatedAt`) so the Needs-your-input tab is one bounded query.
2. **Mapping.**

   | Old state + condition | New state | needsInput / reason |
   |---|---|---|
   | waiting_for_your_ai + ready, disconnected, retry_scheduled | waiting_on_ai | false |
   | working + active | ai_working | false |
   | needs_you + awaiting_user | waiting_on_ai (lease already released) | true / question |
   | needs_you + failed | waiting_on_ai | true / failed |
   | needs_you + expired | waiting_on_ai | true / expired |
   | needs_you + anything else (defensive) | waiting_on_ai | true / disconnected |
   | done + completed | answered | false |
   | done + canceled | answered, `archivedAt = canceledAt ?? updatedAt`, condition stays canceled | false |

   The canceled row is the one judgment call: Core has no canceled state, and archive is its
   way of tidying work away. The archived view shows "Canceled" from the condition.
3. **Widen first (release A).** Schema unions accept old and new values; `needsInput` optional.
   Add `normalizeQueueState(item)` in `lib/queue/contract.ts`, the only place the mapping lives.
   Every reader goes through it. Every writer writes only new values. Transitions:
   request_user_action keeps state and raises the flag; complete gains an optional `question`
   so an item can be Answered and flagged; the person's answer (resume) clears the flag and
   leaves the state alone; failure and expiry raise the flag with a reason; cancel becomes
   archive. New activity events `needs_input_raised` and `needs_input_cleared`; old rows are
   never rewritten (append-only), and presentation maps old `fromState`/`toState` strings to new labels.
4. **MCP compatibility.** `family_history_get_queue` accepts the new states plus a `needsInput`
   filter, and for one release also accepts the old values as aliases (`needs_you` means
   `needsInput: true`; the other three map one to one). Responses carry `state`, `needsInput`,
   `needsInputReason`, and for that release a `legacyState`. Update catalog descriptions, `/ai`,
   `/ai.txt`, and the brief's grouping. Keep `check:public-ai-truth` green.
5. **UI.** Tabs in Core order: Waiting on AI · AI working · Needs your input · Answered ·
   Everything (last). Default list is unprocessed work. The flag is also marked on each row,
   with the question answerable in place. Counts per tab from bounded indexed queries.
6. **Backfill.** Internal mutation (for example `queueMigration.backfillQueueVocabulary`) run
   per owner over `by_owner` in batches of 100 with a cursor; dry-run mode returns counts per
   mapping row; idempotent (skips rows already migrated); writes `legacyState` and
   `legacyCondition` on each row so a paired reverse mutation can restore them. Prove it in
   Local Sandbox on marked synthetic rows covering every row of the mapping table first.
7. **Narrow (release B).** When a production dry run reports zero old values, remove old
   literals from schema and validators, drop the MCP aliases and `legacyState`, retire
   `awaiting_user`, and update the Project Philosophy Queue section.
8. **Tests to update.** All files listed under Current truth, plus new ones: the mapping table
   as a unit test; backfill idempotency and reverse; Answered plus needsInput; resume clears the
   flag without changing state; MCP alias acceptance; tab order.
