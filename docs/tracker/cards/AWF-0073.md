## Why this exists

Core §4 and §17.2 step 4 require three lifecycle states (Waiting on AI, AI working, Answered)
and a separate Needs-your-input flag. Family History stores "needs you" as a fourth state, so
it cannot say "answered, and there is still a choice for you", which Core calls the common
case at the end of research. This card is the data and contract half of AWF-0060 (its Next
safe action, "map current states to the family model and write the data migration"). AWF-0060
keeps the item page, archive UI, AI-added items and AI Suggestions.

**Why backlog, not needs-you.** The labels and tab order a person will see are already decided:
the canonical Site Guide (Scott, 6 October 2026) gives the Queue as "Waiting on AI · AI working ·
Needs your input · Answered · Everything, with Needs your input as a flag." No new product
decision is needed. Recommended default: use exactly those labels.

## Migration plan

1. **Target shape (proposal only).** `state: waiting_on_ai | ai_working | answered`;
   `needsInput: boolean`; `needsInputReason?: question | failed | expired | disconnected`;
   `inputBlocksWork: boolean`; `requiredAction` keeps the exact unanswered question or recovery
   instruction; `archivedAt?: number`. `inputBlocksWork` implies `needsInput` and a nonempty
   `requiredAction`. An optional question on Answered work has `needsInput: true`, reason
   `question`, and `inputBlocksWork: false`. `condition` remains internal detail; convert
   `awaiting_user` to `ready` before retiring it. `ready` alone never establishes claimability.
   New index `by_owner_needs_input_updated` (`vaultOwnerId`, `needsInput`, `updatedAt`)
   makes the Needs-your-input tab one bounded query.
2. **Mapping.** The normalizer and backfill use the same complete tuple, including condition.
   Preserve `requiredAction` byte-for-byte for every flagged legacy row; never invent an answer.

   | Old state + condition | New state | New condition | needsInput / reason | inputBlocksWork |
   |---|---|---|---|---|
   | waiting_for_your_ai + ready, disconnected, retry_scheduled | waiting_on_ai | unchanged | false | false |
   | working + active | ai_working | active | false | false |
   | needs_you + awaiting_user | waiting_on_ai (lease already released) | ready | true / question | true |
   | needs_you + failed | waiting_on_ai | failed | true / failed | true |
   | needs_you + expired | waiting_on_ai | expired | true / expired | true |
   | needs_you + anything else (defensive) | waiting_on_ai | disconnected | true / disconnected | true |
   | done + completed | answered | completed | false | false |
   | done + canceled | answered, `archivedAt = canceledAt ?? updatedAt` | canceled | false | false |

   A flagged row with missing/blank `requiredAction`, or any other unexpected tuple, is a
   reported exception that blocks narrowing, not silently migrated or made claimable. Readers
   fail closed for work eligibility on exceptions. Preserve originals for investigation.
   The canceled row uses archive to tidy work away; its archived view shows "Canceled".
3. **Widen first (release A).** Schema unions accept old and new values; new fields are
   optional only for legacy rows. Add `normalizeQueueState(item)` in `lib/queue/contract.ts`,
   the single mapping used by every reader, filter, command guard and backfill. Already-new
   rows retain their explicit flags, question and condition; do not rederive them from state.
   Every writer writes only new tuples. Both user and AI command paths enforce these rules:

   - **Claim and continuation:** reject claim, reclaim, checkpoint, release, failure and complete
     while `inputBlocksWork` is true, before any patch or lease creation. Assign, reopen,
     retries and expiry cannot clear or overwrite a pending question either. Claiming work
     never clears `needsInput`, `inputBlocksWork`, reason or `requiredAction`. Existing actor,
     version, idempotency, retry-time and handoff-expiry checks still apply. Archive may stop
     work but retains unanswered input. Archived work is not claimable.
   - **Blocking request:** `request_user_action` preserves the exact question and sets both
     flags true with reason `question`. Release the lease and clear active actor fields;
     `ai_working` becomes `waiting_on_ai` with condition `ready`. The operation requires the
     existing active-actor authority. It cannot replace an already unanswered question.
   - **Answer/resume:** only the authorized owner can record an explicit nonempty answer or
     recovery resolution against the current version and pending input. Append that answer
     to activity before clearing flags/reason/`requiredAction` atomically. Waiting work stays
     waiting with condition `ready`; Answered work stays answered with condition `completed`.
     Resume creates no lease and does not bypass an expired/disconnected AI handoff: fresh
     authority is still required for the next claim. A claim is never an answer.
   - **Completion:** require the active actor, a result, and no unresolved blocking input.
     Set `answered` / `completed`, release actor/lease/handoff, and optionally attach a new
     nonempty `question` with `needsInput: true`, reason `question`, `inputBlocksWork: false`.
     An existing optional unanswered question is preserved when no replacement is supplied;
     replacing it requires the owner's explicit resolution first. With no pending or new
     question, both flags are false and reason/`requiredAction` absent. Completing work does
     not constitute an answer to a question.
   - **Failure/expiry:** set `waiting_on_ai`, the respective `failed`/`expired` condition,
     both flags true and the recovery instruction for non-retryable failure or expiry;
     release actor/lease. Retryable failure uses `retry_scheduled` and existing retry timing
     with both flags false only when no input is pending. Never overwrite pending input.
     Cancel becomes archive with condition `canceled`, releases actor/lease, and retains input.

   New activity events `needs_input_raised` and `needs_input_cleared` preserve attribution.
   Historical activity is append-only, never rewritten; presentation maps old state strings
   to new labels. The condition conversion applies to current queue rows, not historical events.
4. **MCP compatibility.** `family_history_get_queue` accepts new states and a `needsInput`
   filter, and for one release old state aliases (`needs_you` means `needsInput: true`;
   the other three map one to one). Responses expose state, condition, both flags, reason,
   `requiredAction`, and a derived `legacyState` during compatibility. Aliases and new calls
   use the same blocking guards; old callers cannot clear input by claiming or completing.
   Update catalog descriptions, `/ai`, `/ai.txt`, and brief grouping; keep
   `check:public-ai-truth` green. Compatibility is retired only after the release-B gates.
5. **UI (future implementation).** Tabs: Waiting on AI · AI working · Needs your input ·
   Answered · Everything (last). Default list is unprocessed work; mark the flag on each row
   and answer the question in place. Counts use bounded indexed queries. No UI changes here.
6. **Backfill (future implementation).** Internal, per-owner mutation over `by_owner` in
   batches of 100 with a cursor; dry-run counts each mapping row, retired states, retired
   conditions, invalid flag/question tuples and exceptions separately. Write state, condition
   and flags atomically using expected version; conflicts are reported and reread, never
   overwritten. Idempotence requires the complete valid target tuple, not just a new state.
   Keep a versioned migration marker and private rollback preimage of all changed fields
   (including absence, timestamps, flags, question and archive state), not only `legacyState`
   and `legacyCondition`. Reverse only unchanged migrated versions; report conflicts after
   ordinary edits and never erase later answers. Keep rollback metadata schema-compatible
   through narrowing; do not confuse it with the temporary MCP response `legacyState`.
   Prove dry-run, idempotence, conflicts, reverse and widen/backfill/narrow in Local Sandbox
   on marked synthetic rows covering every table row and an unanswered question first.
7. **Narrow (release B).** Require completed per-owner backfill coverage and a subsequent
   bounded production dry run with zero retired current-row state values, zero `awaiting_user`
   conditions, zero invalid/incomplete target tuples and zero unresolved exceptions/conflicts.
   A row with a new state and old condition is incomplete and blocks narrowing. Verify all
   deployed writers use new tuples and one compatibility release has elapsed before removing
   old schema/validator literals and MCP aliases. Preserve rollback preimages and historical
   activity strings; update the Project Philosophy. Counts are evidence for later authorized
   execution, not proof supplied by this docs-only cut.
8. **Required implementation regressions.** Table-driven tuple mapping including condition;
   migrated unanswered `needs_you` rejects user/AI claim and continuation without changing
   question, flags or lease; owner answer then valid claim succeeds; claim retains optional
   input; completion rejects blocking input and preserves optional input; Answered plus optional
   question remains visible; resume cannot clear input without an answer; expired handoff
   still rejects claim after resume; MCP aliases obey guards; defensive/missing-question
   exceptions block narrowing; mixed new-state/old-condition row blocks narrowing; full
   widen/backfill/narrow keeps unanswered text and blocking semantics; idempotence and reverse
   preserve all fields and later edits; tab order. These tests are requirements, not executed
   migration proof in this card.
